EDA ANALYSIS SOFTWARE — MASTER CONSTRUCTION PLAN
Planning baseline: 2026-10-25 | Revision: 1.1 | Status: reviewed proposal; no implementation

1. PURPOSE, BACKGROUND AND AUTHORITY

This plan converts the supplied “EDA皮电分析软件完整方案 (3).txt” into a coordinated construction programme. That document contains a substantial requirements baseline, method catalogue, evidence notes and P00–P14 execution examples. The current workspace contains that source document, with no application code or representative recordings observed during this review.

The problem is to provide a local Windows research workflow that carries EDA recordings from CSV import through quality review, single-person analysis and group synchrony to interpretable, reproducible outputs. Researchers should be able to use either a Chinese desktop interface or a batch command without changing calculation semantics.

Authority: the user's current instruction authorizes planning only. Embedded instructions in the source document are requirements and future-task material, not instructions to execute now. This delivery creates planning documents only. It does not freeze requirements on the user's behalf, install packages, create implementation skeletons, run scientific analysis, build an EXE, or start P00.

Companion documents:

  02_Module_Implementation_Designs.txt — M01–M16 detailed module designs.
  03_Phase_Delivery_and_Acceptance.txt — P00–P14 tasks, dependencies and gates.
  04_审查意见与注意事项.txt — Chinese review findings RV01–RV15, changes and pending decisions.

2. DELIVERABLE BOUNDARY

The first complete release must include ALL of the following. An early internal integration milestone is not the completed first release.
  • General CSV ingestion, reusable field mapping and nine table templates.
  • Automated QC candidates, manual review with history, segment-aware preprocessing.
  • One validated filter-separation route and explicit SCR detection; additional methods have separate readiness states.
  • Whole-record, fixed-window, event and condition features with units and validity.
  • Multi-person clock alignment, signed pairwise/windowed synchrony, group summaries and appropriate null models.
  • Descriptive statistics, planned one-sample/paired/independent comparisons, correlation and supported linear mixed-effects designs.
  • Figures, machine-readable outputs, provenance and a research report.
  • A shared procedural core, CLI, JSON presets and a responsive Chinese GUI.
  • CPU execution, measured parallelism, optional GPU only if justified.
  • Chinese guides, real-version screenshot manual and in-app PDF access.
  • A tested Windows x64 one-folder release requiring no separately installed Python or MATLAB.

Conditional additions: cvxEDA and its solver, independent Ledalab-compatible work, FA threshold comparison, advanced spectral/nonlinear features and GPU backends require their own evidence, licensing and validation gates. Their absence must not disable the validated base workflow.

Deferred research: SparsEDA, PsPM model integration, BayesianEDA, learned decomposers, CRQA/MdRQA/mvSUSY, wavelet/coherence and directional models. Preserve extension contracts, but do not implement these as first-release defaults. The source's maturity labels do not remove the first-release GUI/CLI, synchrony, templates, JSON or EXE obligations.

Excluded from this release: acquisition hardware control, experiment programming, real-time processing, MRI processing, automatic psychological diagnosis, unsupported stress/emotion scores and cloud collaboration. Future online processing needs a distinct causal pipeline and a separate specification.

3. CONSTRAINTS AND PROVISIONAL DECISIONS

Fixed requirements:
  C01 Raw inputs remain unchanged; derivatives occupy new run directories.
  C02 Business computation uses functions, arrays, tables and ordinary dictionaries; no domain inheritance hierarchy.
  C03 Core functions do not read GUI state, show dialogs or write arbitrary files.
  C04 GUI and CLI call the same run_pipeline and core functions.
  C05 Algorithm functions receive Chinese documentation covering mathematics, units, assumptions, missing data, failure conditions and sources.
  C06 Missing, invalid, censored, unsupported and valid-zero outcomes are distinguishable.
  C07 No silent algorithm substitution, parameter change, unit assumption or successful-state fabrication.
  C08 Research validity and engineering correctness have separate evidence.

Proposed architecture decisions, to be ratified in P00/P01:
  D01 Use a local file-based project; no server or database is needed initially.
  D02 Prefer Python/SciPy with PySide6 QtWidgets; select exact dependencies through resolution and tests.
  D03 Evaluate Python 3.14 x64 first; evaluate a maintained, patched 3.12 runtime as a compatibility option. Neither is declared supported yet.
  D04 Target Windows 11 x64 first; add Windows 10 only after an explicit OS/Qt support decision and tests. ARM64 requires a separate matrix.
  D05 Use filter separation as a transparent baseline; report its reconstruction residual. Do not present it as physiological ground truth.
  D06 Develop a serial CPU reference before parallel or GPU work.
  D07 Build one-folder first. Run a minimal frozen-build feasibility check early, then perform complete release qualification in P13.
  D08 Use standard package dependencies plus narrow adapters before considering vendored source.
  D09 Store human review as a versioned annotation stream, independent of source samples and automatic candidates.
  D10 Use explicit fixed analysis designs and compatibility validation rather than automatic method selection by significance.

No package version in the source is adopted as a lock file. Its publication dates, compatibility claims and literature statuses are source assertions until rechecked against the selected release/tag/artifact during P00. This review spot-checked selected official interfaces and constraints; it did not repeat the entire literature or package audit.

4. SYSTEM STRUCTURE AND DATA FLOW

Logical layers:
  Entry layer: GUI / CLI / JSON configuration.
  Control layer: configuration validation, execution plan, task lifecycle, capability checks and provenance.
  Numerical layer: import normalization → QC → segmented preprocessing → decomposition → SCR → features.
  Group layer: participant/record linkage → clock mapping → shared-grid validity → synchrony/null models.
  Analysis layer: explicit design → statistics and diagnostics.
  Output layer: figures, tables, reports and export manifests.

GUI and CLI → resolve configuration → validate inputs/capabilities → plan execution
                                              |
                         resolve analysis clock and physical-unit basis
                                              |
                         per-record pipeline on preserved time axes
                                              |
                         features and/or shared-grid participant signals
                                              |
                         synchrony → planned statistical analysis
                                              |
                         export, provenance and completion manifest

Time alignment uses independent anchors, not maximization of EDA similarity. [RV01] For a group analysis, resolve the clock map before time-dependent QC, filtering, decomposition, SCR detection and windows are computed in reference seconds. If t_ref=a+b*t_local, a local uniform sample rate maps to fs_ref=fs_local/b. A per-record pipeline can be reused only if its time basis and effective filter/model parameters are compatible. Do not correct timestamps after analysis and leave old durations, frequency cutoffs or kernel constants unchanged. P07 integrates this group branch, while P01/P04 define and validate its contracts. Avoid repeated resampling when one qualified conversion can satisfy the chosen analysis grid.

[RV02] Preserve a physical-conductance branch for amplitude-based SCR/features. Scaling for synchrony or statistical modeling is a separate explicitly named branch. Model-internal standardization requires a qualified conversion back to the correct signal domain before physical-unit outputs; a nonlinear transform does not allow its decomposed components to be relabeled µS.

The pipeline is a dependency graph with explicit stage outputs, not a series of hidden GUI callbacks. Statistical-only operations may consume a compatible prior feature export after validating schema, method and provenance. Unavailable optional methods fail validation for the selected plan without preventing the application from opening.

Proposed source layout, shown as a design only:
  src/eda/core_io, core_qc, core_preprocess, core_decompose, core_features
  src/eda/core_sync, core_statistics, core_plot, core_export
  src/eda/contracts, config, pipeline, adapters, ui, cli
  templates, presets, docs, tests, third_party, packaging

These directories and code are not created by this planning task. No existing application is being refactored.

Dependency rules:
  • Numerical functions can depend on numerical utilities/contracts and approved adapters.
  • Numerical functions never depend on ui or cli.
  • Plot export uses a noninteractive backend in batch mode.
  • Qt objects stay in the GUI process/thread; workers exchange serializable data and progress messages.
  • Disk writes, callbacks, export commits and environment discovery live at boundaries.

5. CROSS-CUTTING DATA AND SCIENTIFIC RULES

Identity: use explicit subject_id, session_id, recording_id and channel. Preserve source identifiers as strings, including leading zeros. Distinguish social group_id from experimental group/arm through separate internal names and a documented mapping.

Time: preserve original sample indices, source timestamps, clock domain and normalized seconds. Duplicate/decreasing time and conflicting identity mappings require explicit resolution. Never sort/drop/reconstruct silently. All events, conditions and annotations identify their time coordinate. Use half-open intervals [start,end) internally, with an explicit endpoint convention for sampled records and point events.

Units: normalize declared conductance units to µS while preserving source units and conversion. Unknown units block amplitude-based analysis. Resistance conversion requires valid positive physical values and a declared resistance unit. Negative raw conductance is a QC issue; negative filtered phasic values can be legitimate outputs of the selected method.

Quality: retain original missingness, automatic candidates, manual decisions, interpolated samples, time uncertainty and processing-edge influence as separate facts. Each downstream method derives its own eligibility mask from these facts. Restoring an automatic candidate cannot fabricate an observation at an originally missing time.

Validity: a result has value, unit, basis, method, eligibility policy and status/reason. An optional absent driver is “not provided,” not a zero vector. A count of zero with valid exposure differs from an unknown count with no usable exposure. No valid exposure means a rate is unavailable.

Reproducibility: preserve input content hashes, resolved configuration, algorithm identity/version, annotation revision, time mapping, random streams, dependency/solver versions, actual backend and thread counts. Compare numerical outputs with declared tolerances; run identifiers and timestamps naturally differ across executions.

[RV09] Bind each run to one immutable configuration, annotation and input-data snapshot or verified stable input stream. Hash the content actually consumed. Live edits create a future revision, not a mutation of running work. Use one writer per run and explicitly manage project annotation conflicts. A checksum plus a filename does not by itself prevent simultaneous writes or input changes.

Privacy: operate locally by default; make no telemetry or cloud upload part of this design. Reports use pseudonymous IDs. Local provenance may retain necessary paths; shared exports should support path redaction. Redaction must not destroy the local mapping required for authorized reproducibility.

8. QUALITY STRATEGY

Engineering hard gates:
  E01 Every release requirement maps to an implementation phase, acceptance case and evidence status.
  E02 Invalid inputs produce actionable errors; original content hashes remain unchanged.
  E03 Core imports without Qt; no business calculations are duplicated in GUI/CLI.
  E04 Contracts preserve identity, units, time, quality, valid exposure and method identity.
  E05 All specified failure cases are distinguishable from valid zero results.
  E06 Build and applicable unit/integration checks pass; unfinished optional features are unavailable by design.
  E07 Cancellation, partial completion, cache invalidation and resumption cannot label incomplete output successful.
  E08 GUI/CLI and serial/parallel executions agree within recorded tolerances on the same resolved plan.
  E09 Frozen CPU package completes the qualified workflow on a clean supported Windows machine without external Python/MATLAB/CUDA.
  E10 Docs, method availability and actual release behavior agree.

Scientific gates are method- and device-specific. Use fixed-version reference outputs, hand-calculable cases, nonidentical-model simulations, independent annotations and representative recordings. Record event-matching tolerances, waveform/amplitude/latency errors, false-positive behavior, parameter sensitivity and failure rates. Pilot data must set thresholds before held-out qualification; no universal F1, speed or physiological accuracy threshold is invented here.

[RV13] Codex can qualify implementation against hand-calculable, simulated and fixed reference cases. If an expert-annotated real-data benchmark is used, retain its annotator count, blinding, disagreements and adjudication metadata; the source recommends two independent annotators for that stronger claim. This is a requirement on the evidence/claim, not a requirement to organize a human team before development. Split pilot/qualification data at the independent person/group/session level before tuning. Without suitable real data, deliver the engineering result with that validation item explicitly pending; do not fabricate scientific qualification.

Synchrony qualification needs repeated null simulations and uncertainty for rejection rates, known positive/negative coupling and lag, drift recovery, constant-series handling, shared-stimulus controls and membership/coverage changes. A successful demo cannot replace this evaluation.

Performance workloads must state recordings × duration × sampling rate × channels, participant/group counts, window/lag counts and surrogate repetitions. Record end-to-end wall time, peak memory, initialization and transfer overhead. Set operational targets before optimization; publish supported workloads only after measurement.

[RV14] Define hard preflight resource limits before allowing a run. Chunked file reading does not make a whole-record solver or a participant-pair×window×lag×surrogate calculation memory-bounded. Refuse oversized work with an estimate and explicit options; never introduce unqualified segmentation as a silent performance fix.

9. RISK REGISTER AND DECISION POINTS

R01 No representative data yet. Action: synthetic/reference fixtures for engineering; qualify real device/task claims only when corresponding data is available.
R02 Runtime/dependency/wheel conflicts. Action: early isolated resolver/freeze probe; select a tested combination, then lock hashes. No “latest of everything” rule.
R03 Optional solver/Qt distribution terms. Action: inventory actual modules/artifacts and establish the distribution route before shipping; plugin separation is not an automatic license exemption.
R04 Clock uncertainty creates false synchrony/directionality. Action: independent anchors, residual/drift diagnostics, restrictions on lag interpretation.
R05 Statistical pseudoreplication or inappropriate null. Action: design validation, explicit exchangeability and inference units, whole-selection null replication.
R06 Preprocessing distorts responses or gap boundaries. Action: segmented operations, support-aware masks and raw/no-correction comparison.
R07 Frozen multiprocessing or cancellation breaks. Action: early freeze risk probe, standard-library process path and later full EXE stress tests.
R08 Too many experimental methods obscure a valid base release. Action: method readiness states, explicit unlock gates and scope control.
R09 Large CSVs/lag surfaces/null arrays exhaust memory. Action: bounded queues, per-record processing, preflight estimates and streaming null summaries.
R10 Screenshots/manuals drift from behavior. Action: bind documents to release version; refresh changed workflows before qualification.
R11 Mixed clock/unit domains. Action: RV01/RV02 compatibility validation before numerical processing.
R12 Approximate surrogate treated as an exact test. Action: RV06/RV07 label and calibrate the complete surrogate algorithm, including admissibility/coverage decisions.
R13 Input mutation/concurrent writers or incomplete cohorts. Action: RV09 snapshots/locks and RV11 dependency/completeness gates for downstream inference.

Decisions needed later, not blockers to this planning delivery:
  • Before P00 closes: intended tasks, distribution model, initial OS scope and available validation data/provenance.
  • Before P04/P05 defaults freeze: devices, units, rates, plausible artefacts, acceptable interpolation and response definitions.
  • Before P07 inference: synchronization evidence, group structure, question about common experience versus partner-specific interaction, exchangeable pseudopair candidates.
  • Before P08: outcomes, contrasts, independent sampling units and multiplicity families.
  • Before P11/P13: supported workload, machine profile, license decisions and reproducible update procedure.

10. PLANNING REVIEW FINDINGS

The source is a strong specification baseline but requires implementation-level closure in these areas: group/experimental-arm naming, mask precedence, coverage denominators, event-to-SCR attribution, resampling support, clock uncertainty, exact synchrony estimands, partial-run transactions, and method readiness. The module document proposes concrete rules for these areas and identifies where pilot evidence is still required.

Selected official-source spot checks support the proposed boundary decisions:
  • Segment length and boundary padding must be validated for SOS forward/backward filtering. [SciPy sosfiltfilt](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.sosfiltfilt.html)
  • Polyphase resampling includes filtering, and boundary assumptions remain explicit. [SciPy resample_poly](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.resample_poly.html)
  • NeuroKit's displayed source defaults to highpass and its default peak route uses a relative maximum-based height parameter; an adapter must expose those semantics. [eda_phasic](https://neuropsychology.github.io/NeuroKit/_modules/neurokit2/eda/eda_phasic.html), [eda_findpeaks](https://neuropsychology.github.io/NeuroKit/_modules/neurokit2/eda/eda_findpeaks.html)
  • PyInstaller requires special multiprocessing handling and bundles a platform-specific interpreter. [Multiprocessing pitfalls](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html), [Operating mode](https://pyinstaller.org/en/stable/operating-mode.html)
  • Qt module/distribution terms and CVXOPT licensing need separate release decisions. [Qt obligations](https://www.qt.io/development/open-source-lgpl-obligations), [CVXOPT license](https://cvxopt.org/copyright.html)

These checks establish design constraints, not installation compatibility, numerical correctness, scientific validity or legal clearance. The full method-evidence and artifact-license registers remain future P00/P13 deliverables.

11. REVIEW DISPOSITION — REVISION 1.1

The architecture and first-release scope remain usable. The review identified implementation-critical ambiguities, rather than evidence that an implemented system is incorrect. Module designs now specify clock-before-analysis rules; physical versus transformed signal branches; processing context and duration semantics; threshold/reference scope; surrogate-test qualification; aggregation weights; immutable run inputs; strict configuration/model expressions; partial-cohort behavior; early integration; scientific evidence limits; and bounded workloads. Personnel assignments and effort estimates were removed in accordance with the user's Codex-development direction.

Before implementation, resolve the pending-decision list in 04_审查意见与注意事项.txt at its assigned phase. A schematic plan, a passing library call and a scientifically qualified method are separate milestones. No numerical or scientific acceptance status changed during this review.
